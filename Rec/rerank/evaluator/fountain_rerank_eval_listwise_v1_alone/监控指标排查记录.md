## 2026-08-18：按消费长度拆分的 Prefix 匹配监控（历史旧口径）

> 状态：已废弃。该批监控把 `fountain_fulllink_rerank_index_list` 的前 K
> 个 item 当成真实曝光 Prefix，没有使用 `real_show` 筛选并按
> `real_show_index` 恢复最终曝光顺序。以下表格仅保留作历史对照，不能再
> 解释为真实 Prefix 的覆盖率或训练保留率。

### 业务口径

- 模型候选 List 和监督张量的固定长度为 6。后续补充日志发现，原始请求的 `real_show=1` 数量也可以为7；当前实现会将其裁剪为前6个位置，见后文边界样本记录。
- `K` 是请求中 `real_show=1` 的数量。
- 当时曾假设 `real_show=6` 对应的完整曝光 List 必然存在于候选集中；后续日志证明，按最终曝光顺序重建后该假设并不总成立。
- K1～K5 只有不完整的曝光 Prefix。受后续端排调整影响，真实 Prefix 不一定存在于原始候选 List 中。

### 指标定义

- `match/by_k/kK_request_rate`：真实消费长度为 K 的请求，在所有有效曝光请求中的占比。
- `match/by_k/kK_any_prefix_match_rate`：在长度为 K 的请求中，30 个候选 List 里至少有一个候选的前 K 个 item 与真实曝光顺序完全一致的比例。它也是该 K 下的训练请求保留率。
- `match/by_k/kK_max_score_prefix_match_rate`：在长度为 K 的请求中，旧分最高的候选 List 本身就能匹配真实曝光 Prefix 的比例。

### 当时观测（旧口径）

| K | 原始请求占比 | 任意候选匹配率 | 旧分最高候选匹配率 |
|---|---:|---:|---:|
| 1 | 约 9.8% | 约 91% | 约 89% |
| 2 | 约 7.2% | 约 76% | 约 74% |
| 3 | 约 7.2% | 约 62% | 约 61% |
| 4 | 约 9.7% | 约 43% | 约 42% |
| 5 | 约 20.5% | 约 33% | 约 32% |
| 6 | 约 45.5% | 约 98.6% | 约 98.6% |

### 结论

1. K1～K5 的匹配率随 Prefix 变长而下降，符合“比较位置越多，越容易受端排调整影响”的预期。
2. 旧口径下 K6 匹配率接近 100%，主要因为直接使用了原数组前六项；它不能证明按最终曝光顺序重建后的完整 List 也存在于候选集中。
3. `any_prefix` 和 `max_score_prefix` 的差距仅约 0～2 个百分点。在能找到匹配候选的请求中，旧分最高候选通常已经能匹配；遍历全部 30 个候选只额外挽回少量请求。
4. Prefix 匹配 mask 会产生明显的长度选择偏差。按当前截图粗略换算，过滤后的训练长度分布约为 K1=12%、K2=7%、K3=6%、K4=6%、K5=9%、K6=60%。原始样本中占约 45.5% 的 K6 被放大，占约 20.5% 的 K5 被压缩到约 9%。
5. 这些是数据和 mask 质量指标，不是模型收敛指标。曲线随 step 变化主要反映 batch 波动、样本时段变化或上游数据漂移。
6. 只看匹配样本上的离线 AUC，会忽略未匹配请求并改变原始长度分布，因此不能单独代表全量请求上的时长预估水平。

### 历史待排查项（已完成）

- 已确认核心问题不是 `+1` 偏移，而是旧逻辑没有用 `real_show` 筛选 item，也没有按 `real_show_index` 恢复最终曝光顺序。
- `real_show_index` 是 item 在最终 RecoResult/曝光结果中的位置编号；它不是候选池坐标，不要求从 1 开始，不要求连续，也不受当前60个 item 的数组长度限制。
- 正式训练口径和新的监控定义见下一节。

## 2026-08-18：`real_show_index` 语义确认与正式训练口径

### 字段与重建规则

- `context_info__real_show_list[i]`：原始 item 槽位 `i` 是否获得真实曝光。
- `context_info__real_show_index_list[i]`：同一 item 在最终结果/曝光序列中的位置编号，只用于确定曝光 item 之间的先后顺序。
- `fountain_fulllink_rerank_index_list[i]`：同一 item 在模型统一候选池中的坐标，用于和30条候选 List 的 item index 对齐。
- 三个数组按原始槽位 `i` 一一对应。正确恢复方式是：先用
  `real_show[i] == 1` 筛出曝光 item，再按 `real_show_index[i]` 升序排列，
  最后读取相同槽位的 fountain candidate index。
- 原始数组中的存储顺序不重要，但送入 List 模型的曝光 Prefix 必须保持上述真实顺序；List 模型包含位置编码和因果 Prefix 建模，不能只比较无序 item 集合。

### Debug 日志证据

并包含上述19条旧样本。

| Step | 关键现象 | 说明 |

| 680 | 原始曝光 rank 为 `[20,24,21,22,23]`；candidate 13 被重排到最后 | 再次证明即使 `real_show` 位于前 K 项，也仍需按 rank 排序 |
| 620 | 排序后的 rank 为 `[28,30,31,32,33,34]`，中间缺少29 | 证明 rank 允许有间隔，“必须连续”的监控口径错误 |

| 460 | 5个 `real_show=1` 对应的 rank 全为0 | 排序后 rank 不是严格递增，`factual_rank_valid` 应将该请求排除 |

83条完整抽样的汇总结果：

- 71/83 条旧顺序与重建顺序相同，12/83 条发生变化，抽样变化率约14.5%，与全量 TB 中约14%的顺序变化一致。12条变化中，8条由 `real_show` 槽位中间存在0导致，4条由曝光 rank 乱序导致。
- 82/83 条的曝光 rank 排序后严格递增；唯一异常是 step 460 的5个曝光 rank 全为0。另有23/83 条的 rank 存在间隔，最大 rank 为375，进一步证明 rank 无需连续，也不受60长度限制。
- 重建 Prefix 在候选 List 中命中42/83条，抽样命中率约50.6%；旧序列命中49/83条。其中42条新旧都命中，7条仅旧序列命中，没有“仅重建序列命中”的抽样；这说明旧口径会高估候选集对事实曝光顺序的覆盖。
- 上述50.6%只是83条定期抽样的诊断值，不替代全量 TB 统计；正式覆盖率仍以全量 TB 的约62.8%为准。
- step 610 说明“旧、新序列都能命中候选”也不代表旧序列正确：两者实际命中了不同的首 item，真实监督必须采用重建序列。

### 补充日志暴露的边界项

- step 460 说明上游可能传入重复/缺失的曝光 rank。当前 `factual_rank_valid` 会因“排序后不严格递增”将该请求从训练中过滤，长期应继续观察 `match/factual_rank_valid_rate`。
- step 530 和800的原始 K 为7。当前实现会将 `consume_depth` clip 到6，重建、Prefix 匹配和 loss 都只使用 rank 最小的前6个 item；同时 `by_k/k6_any_prefix_match_rate` 会把原始 K≥6 的请求都计入 K6。因此该指标更准确的含义是“有效消费深度为6（原始 K≥6）”，不是严格的“原始 K=6”。
- 需后续确认 K>6 是合法业务样本还是上游异常。如果合法，建议增加 `raw_realshow_count_gt_list_size_rate` 或独立的 K>6 请求率，避免被 K6 曲线静默合并。

### 正式训练与评估口径

- 所有 List 训练目标统一只使用“rank 有效且重建 Prefix 能命中30个候选 List”的请求，当前全量保留率约62.8%。
- 多个候选共享真实 Prefix 时，仍选择其中旧分最高的候选承接监督。
- 同一匹配 mask 同步作用于长度、Prefix WT/Engagement、List 总价值和单调性 loss。
- 非 legacy 的 List 离线指标使用同一可信匹配 mask；`*_legacy_max_score` 继续保留历史旧分最高 List 口径，仅用于横向对照。
- 本批附件中的 AUC 来自切换前的诊断任务：当时重建序列只做监控，实际训练和主指标仍使用旧的“原数组前 K 项”口径。因此这些 AUC 不能视为新62.8%训练口径的效果，需等待新任务重新验证。

### 保留监控

- `match/observed_prefix_rate`：存在至少一个真实曝光 item 的请求比例，应接近1。
- `match/prefix_match_rate`：rank 有效且重建 Prefix 至少命中一个候选的请求比例；也是实际训练请求保留率，预期约62.8%。
- `match/training_request_drop_rate`：未进入 List 训练的请求比例，是 `1-prefix_match_rate`，预期约37.2%。
- `match/factual_rank_valid_rate`：曝光 rank 非负且排序后严格递增的比例；允许 rank 有间隔，预期接近1。
- `match/by_k/kK_any_prefix_match_rate`：各有效消费长度 K 下，重建 Prefix 的候选覆盖率。K1～K5 等于原始 `realshow_count`；K6 由于 `consume_depth` 被 clip 到 `LIST_SIZE=6`，实际包含所有原始 K≥6 的请求。
